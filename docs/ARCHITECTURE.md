## 2. 服务拆分策略

MVP阶段采用**模块化单体**架构，按业务领域划分模块：

```
openwork/
├── backend/                    # FastAPI 后端
│   ├── app/
│   │   ├── main.py            # FastAPI 入口
│   │   ├── core/              # 核心配置、安全、依赖注入
│   │   │   ├── config.py      # 环境变量配置
│   │   │   ├── security.py    # JWT、加密、哈希
│   │   │   └── deps.py        # 依赖注入（DB session、当前用户）
│   │   ├── modules/           # 业务模块
│   │   │   ├── auth/          # 用户认证与注册
│   │   │   ├── intent/        # AI意图建模
│   │   │   ├── contract/      # 任务合约管理
│   │   │   ├── market/        # 任务市场
│   │   │   ├── acceptance/    # AI验收引擎
│   │   │   ├── payment/       # 资金托管与结算
│   │   │   ├── credit/        # 信用评分
│   │   │   └── blockchain/    # 链上存证
│   │   ├── models/            # SQLAlchemy ORM 模型
│   │   ├── schemas/           # Pydantic 请求/响应模型
│   │   ├── db/                # 数据库连接、迁移
│   │   └── utils/             # 工具函数
│   ├── alembic/               # 数据库迁移
│   ├── tests/                 # 测试
│   └── requirements.txt
├── frontend/                   # Vue3 前端
│   ├── src/
│   │   ├── views/             # 页面组件（P1-P10）
│   │   ├── components/        # 通用组件
│   │   ├── api/               # API 请求封装
│   │   ├── stores/            # Pinia 状态管理
│   │   ├── router/            # 路由配置
│   │   └── utils/             # 工具函数
│   └── package.json
├── docs/                       # 项目文档
│   ├── ARCHITECTURE.md
│   ├── openapi.yaml
│   └── 可信任务市场 产品设计文档 V1.0.docx
└── docker-compose.yml
```

模块间通信规则：
- 模块通过**服务接口**调用，不直接访问其他模块的数据库表
- 异步事件通过 Redis Pub/Sub 传递（验收完成→触发结算、结算完成→更新信用）
- 所有模块共享同一 PostgreSQL 数据库，但逻辑上隔离

## 3. 技术选型决策矩阵

| 维度 | 权重 | PostgreSQL | MySQL | MongoDB |
|------|------|-----------|-------|---------|
| JSON字段支持 | 25% | 9 (JSONB原生) | 5 | 9 |
| 事务一致性 | 25% | 9 | 9 | 6 |
| 生态与工具 | 20% | 9 | 8 | 7 |
| 运维成熟度 | 15% | 8 | 9 | 7 |
| 扩展能力 | 15% | 8 | 7 | 9 |
| **加权得分** | | **8.55** | **7.60** | **7.55** |

**决策：选择 PostgreSQL** — JSONB 支持优秀，适合存储意图蓝图、验收标准等半结构化数据；事务一致性强，适合资金流场景。

### 核心聚合

| 聚合根 | 包含实体 | 不变量 |
|--------|---------|--------|
| Contract（合约） | Deliverable、IntentBlueprint | 状态只能按规则流转；发布前必须有蓝图 |
| User（用户） | CreditProfile | 信用分在0-100之间 |
| Transaction（交易） | — | 金额>0；托管→释放必须有对应验收通过记录 |
| AcceptanceRecord（验收） | — | 最多3次验收；结果只能是pass/fail |

## 5. 核心数据流

```
雇主输入需求（自然语言）
    ↓
[意图建模模块] AI多轮追问 → 生成2C1H蓝图
    ↓
[合约模块] 蓝图 → 生成交付物清单+验收标准
    ↓
[支付模块] 雇主支付 → 资金托管冻结
    ↓
[市场模块] 任务发布 → 自由职业者浏览+接单
    ↓
[合约模块] 状态: 已发布→已接单→执行中
    ↓
[合约模块] 自由职业者上传交付物
    ↓
[验收模块] AI逐项检查 → 生成验收报告
    ├─ 全部通过 → [支付模块] 自动结算 → [信用模块] 更新信用分 → [存证模块] 上链
    └─ 存在不通过 → 退回修改（最多3次）→ 超限人工审核
```

## 6. 质量属性分析

| 质量属性 | 目标 | 实现方案 |
|---------|------|---------|
| 性能 | 页面加载≤2s，AI响应≤3s | Redis缓存、异步LLM调用、数据库索引优化 |
| 可靠性 | 可用性≥99.9% | 健康检查、优雅关闭、数据库连接池 |
| 安全性 | 数据加密、防攻击 | JWT认证、AES-256加密敏感数据、HTTPS、限流 |
| 可维护性 | 模块化、可测试 | 依赖注入、模块边界清晰、单元测试覆盖≥80% |
| 可观测性 | 全链路追踪 | 结构化日志、请求ID追踪、Prometheus指标 |

## 7. 架构决策记录（ADR）

### ADR-001: MVP阶段使用模块化单体而非微服务

**状态**：已接受

**背景**：项目处于MVP阶段，团队规模小，需要快速迭代验证产品假设。

**决策**：采用模块化单体（FastAPI），按业务领域划分内部模块。

**备选方案**：
- 微服务：独立部署、独立扩展，但增加运维复杂度和网络开销
- 单体：简单但模块边界模糊，容易变成大泥球

**理由**：模块化单体兼顾开发速度和架构清晰度。模块通过服务接口通信，V2.0可按需拆分为独立服务。

### ADR-002: 选择联盟链而非公链

**状态**：已接受

**背景**：需要关键节点哈希上链存证，要求低成本、高TPS、无需Gas费。

**决策**：使用蚂蚁链/腾讯云区块链（联盟链）。

**备选方案**：
- 以太坊公链：去中心化程度高，但Gas费贵、TPS低
- 自建链：完全可控，但运维成本高

**理由**：联盟链满足企业级存证需求，无需用户持有加密货币，接入成本低。

### ADR-003: 选择FastAPI而非Django

**状态**：已接受

**背景**：项目需要大量AI服务集成（LLM对话、文档解析），需要高性能异步框架。

**决策**：使用FastAPI。

**备选方案**：
- Django REST Framework：生态成熟，但同步模型不适合大量IO密集型AI调用
- Flask：轻量但缺少原生异步和类型验证

**理由**：FastAPI原生支持async/await，Pydantic自动验证请求/响应，自动生成OpenAPI文档，与LLM API调用场景天然契合。

## 8. MVP到V2.0演进策略

```
V1.0 (当前) — 模块化单体
    │
    ├── V1.1 — 效果奖金自动追踪（新增预言机模块）
    │
    ├── V1.2 — 分润对赌（扩展支付模块）
    │
    └── V2.0 — 按需拆分微服务
         ├── 独立支付服务（高可用要求）
         ├── 独立AI服务（GPU资源隔离）
         └── 独立存证服务（区块链节点独立部署）
```

拆分标准：当某模块的部署频率、扩展需求或团队规模独立于其他模块时，将其拆分为独立服务。
